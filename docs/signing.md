# 申込内容の改ざん防止は、誰が署名するかで決まる

多段呼び出しの途中にいる AI による書き換えを防ぐために、署名や通信路の保護のどれが使えるかを比べる。

**この文書の読み手:** 方式を選ぶ設計者。HTTP、TLS、署名の基本を知っている。読んだ後に、守りたい相手に対して、どの方式が効くかを説明できる。窓口の改ざん対策（訂正印、契印、割印など）との対応は、[設計 2-2](research/dx-design.md) にある。用語は[用語集](research/glossary.md)にある。

## 要旨
- **守る相手が中継者（AI）なら、利用者の端末が署名する方式だけが効く（推定）。**
- **mTLS と、AI や MCP による署名は、書き換えた張本人が正規の送信者になるため、防げない（推定）。**
- **採用は、内容を JCS で正規化し、そのハッシュを passkey に署名させる方式。** 署名は 2 段（意向確認、申込み）に置く。
- **署名前の確認画面は、署名する側（顧客のアプリ）が描画する。** passkey の標準画面が取引内容を出す仕組みは、読んだ範囲で確認できなかった（F-G8）。

## 守る相手によって、効く方式が違う
| 方式 | 通信路の書き換え | 票の盗用 | 中継者（AI）の書き換え |
|---|---|---|---|
| mTLS（F-G5） | 防げる（TLS の性質） | 証明書に結んだ票なら、防げる | 防げない（推定） |
| DPoP（F-G4） | TLS に依存する。proof の対象は HTTP メソッドと URI だけ | 鍵を持たない第三者の再利用を防げる | 防げない |
| AI や MCP による HTTP の署名（F-G19） | 署名した構成要素については、防げる | 別の仕組みが要る | 防げない（推定） |
| 利用者の端末による署名（JWS、WebAuthn） | 防げる | 別の仕組みが要る | 防げる（利用者の鍵が端末から出ない前提） |

署名の鍵を持つのが中継者自身なら、書き換えた内容にも正しい署名が付く（推定）。署名が示すのは「誰が送ったか」であり、「本人が何を承認したか」ではない。

RFC 9421 は、エンドツーエンドの完全性と真正性を目的に挙げる。ただし、中継者が通信を作り直し、署名の対象を解析して書き直すと、検証に失敗する（F-G19）。MCP は、バックエンドへ新しい要求を作る。そのため、AI から MCP への署名は、バックエンドまでは届かない（推定）。

## 採った方式は、内容のハッシュを passkey で署名する
手順は次のとおり。署名は、意向確認と申込みの 2 段に置く。
1. 署名する内容を JCS（RFC 8785、F-G20）で正規化し、SHA-256 を取る。意向確認の内容は、選んだ案、案の全体の識別子、意向の値である。申込みの内容は、申込内容と、意向確認の署名の値である。
2. 顧客のアプリが、そのハッシュを challenge にして、passkey で署名させる。
3. バックエンドが、登録された公開鍵で署名を検証し、challenge と内容のハッシュが一致することを確かめる。

内容に署名が結び付くので、経路の途中の誰が運んでも、書き換えは検出される。実装は、[canonical.ts](../packages/shared/src/canonical.ts)（正規化とハッシュ）と [seal.ts](../packages/insurer-backend/src/verify/seal.ts)（署名の検証）、[app.ts](../packages/insurer-backend/src/app.ts)（2 段の連鎖）にある。

## 退けた案とトレードオフ
| 案 | 退けた理由 | 残るトレードオフ |
|---|---|---|
| 取引ごとにトークンを発行（RAR） | 取引ごとに承認と発行が要り、発行回数が増える（推定） | RAR は権限の範囲（契約の種類、上限）に使い、取引ごとには使わない（F-G2） |
| AI や MCP による HTTP の署名（RFC 9421） | 署名者が書き換えた張本人なら防げない。MCP が要求を作り直すと、署名が切れる（F-G19） | 窓口間の通信の保護には使える（推定） |
| Secure Payment Confirmation（W3C） | 取引内容を、ブラウザ自身の画面に出せるが、決済に特化している。仕様は Candidate Recommendation Draft（F-G7） | 仕様が確定すれば、画面の信頼を改善できる。現時点では採用を見送った |

## 限界
- **passkey の画面は、取引内容を出さない（読んだ範囲）:** WebAuthn で、取引内容を認証器の画面に出す仕組みは、読んだ範囲で確認できなかった。ただし、仕様の約 2 割しか読んでおらず、「ない」とは言えない（F-G8）。内容を見せるのは、顧客のアプリの確認画面であり、この画面が乗っ取られると、見せる内容と署名する内容がずれる。
- **署名は、押す前の判断を保証しない:** 利用者が内容を読まずに押せば、検出できない。
- **JWS（RFC 7515）の記述は、未確認である。** JCS は確認した（F-G20）。
- **FAPI 2.0 Message Signing や JAR（RFC 9101）は比べていない:** AI の書き換えへの対策になるかは、未確認である。
- **読んだ範囲:** RFC 9421（F-G19）は先頭の約 4 割、SPC（F-G7）は約半分だけを読んだ。
