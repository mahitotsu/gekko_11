# F-G55. k3d、SPIRE、Envoy の ext_authz、Spring Authorization Server の上で、A（DPoP）から B、C への結び直しと、token-guard の D26、D27 が成り立つ

試作の確かめ（段 0）で、secure と vulnerable の両方の名前空間で、17 項目が期待どおりだった。
- **結び直し（Q2）:** ログインと PKCE と DPoP で受け取った A は、`cnf.jkt` と `may_act` を持った。営業 AI エージェントと事務サービスが替えた B と C は、それぞれの SVID に結ばれ、`act` が入れ子になった（F-G49）。
- **クライアント認証（Q1）:** 認可サーバーは、SVID の SAN の URI で替えを頼む者を認証した。登録のない SPIFFE ID、証明書なし、`actor_token` なし、宛先の違い、段を飛ばした宛先は、拒まれた。
- **組み立て（Q3）:** Envoy は、`forward_client_cert_details` で、相手の SPIFFE ID と証明書のハッシュを token-guard に渡した。token-guard は、DPoP の proof と `cnf` を照らし、出口でトークンを替えた。
- **防御の外し方:** vulnerable では、D26 と D27 を外すと、proof なしの A、別の SVID からの C、許していない SPIFFE ID からの C が通った。secure では、全て拒まれた。名前空間をまたぐ接続は、NetworkPolicy で、どちらからもつながらなかった。

使い方に気をつける点は、F-G50、F-G51、F-G53、F-G54 にある。
