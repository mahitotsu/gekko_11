# F-G90. Keycloak 26.8.1 は、顧客のアプリを JWT-SVID の機密クライアントにすると、認可コードと更新のトークンの交換にクライアント認証を求める。Chromium は http の localhost で __Host-Http- の Cookie を受け付ける。Spring は X-Forwarded-Proto があるとポートを空にする

- `client_assertion_type` に `urn:ietf:params:oauth:client-assertion-type:jwt-spiffe` を使う。`jwt-bearer` では、JWT-SVID に `iss` がないので、Keycloak の中で例外になる。
- クライアント認証のない認可コードの交換と更新は、401 の `invalid_client` で断られる。認証があれば、A は DPoP の鍵（`cnf`）、`may_act`、確認済みの属性、取決めの範囲を保つ。
- 更新のトークンの使い回しは断られ、以後は最新のものも使えない。
- Chromium 156 は、`http://*.localhost` で、`__Host-` と `__Host-Http-` の Cookie を保存する。属性（`Secure`、`HttpOnly`、`SameSite=Strict`）は保たれ、スクリプトからは読めない。
- spring-web の `ForwardedHeaderUtils` は、`X-Forwarded-Proto` があると、スキームを替えてポートを空にし、`X-Forwarded-Port` があればそれで埋める。そのため、BFF から出口の Envoy を通して認可サーバーを呼ぶときは、両方を送らないと、DPoP の `htu` と一致しない。

ほかの版では確かめていない。
