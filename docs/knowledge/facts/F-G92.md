# F-G92. Keycloak 26.8.1 は、RP ID を親ドメインの `<名前空間>.localhost` にした passkey で、登録とログインができ、同じ passkey を顧客のアプリの名前でも使えた。登録はアプリが kc_action で頼める。ただし、resident key の設定に不具合があり、同じ名前の passkey の登録は断る

- **親ドメインの RP ID:** realm の `webAuthnPolicyPasswordlessRpId` を `<名前空間>.localhost` にすると、Chromium 156 は、`http://login.<名前空間>.localhost` で登録した passkey を、`http://app.<名前空間>.localhost` の署名にも使えた。保険会社のシステム（webauthn4j）は、その署名を、Keycloak に登録された公開鍵で確かめられた。
- **登録の頼み方:** 認可の要求に `kc_action=webauthn-register-passwordless` を付けると、パスワードの確かめの後に、登録の画面を出す。登録の画面の文言は、realm の `localizationTexts` で替えられる。
- **passkey でのログイン:** `webAuthnPolicyPasswordlessPasskeysEnabled` を有効にすると、ログインの画面に「パスキーでログイン」のボタンが出る。mediation が `conditional` だと、画面は開いた時点で passkey の待ち受けを始める。仮想の認証器が自動で応じる設定では、画面を開くとすぐにログインが終わった。Windows の VS Code に内蔵されたブラウザでは、待ち受けが数秒後に Windows Hello のダイアログとして出た。その前にボタンを押すと、スクリプトが待ち受けを取り消して始め直し、失敗の知らせ（`webauthn-error-api-not-allowed`）になった。その後に出たダイアログで PIN を入れても、ログインできなかった。mediation を `none` にすると、待ち受けを始めず、ボタンだけで passkey を使う。
- **resident key の不具合:** 登録の画面のスクリプトは、resident key の要否を小文字の `required` と比べる。管理の値 `Required` では一致せず、端末に名前のない passkey（discoverable でない）ができる。`webAuthnPolicyPasswordlessRequireResidentKey` を `Yes`、`ResidentKey` を `not specified` にすると、discoverable な passkey ができた。
- **同じ名前の拒否:** 同じ利用者が、すでにある passkey と同じ名前（`authenticatorLabel`）で登録すると、`webauthn-error-duplicated-device` で断り、登録の画面を出し直す。
- **名前の尋ね方:** 登録の画面のスクリプト（`webauthnRegister.js`）は、passkey を作った後に、名前を `window.prompt()` で尋ねる。設定では切れない。`prompt()` を使えないブラウザ（Windows の VS Code に内蔵されたブラウザ）では、`Error: prompt() is not supported.` で登録が失敗した。ログインの画面のテーマで、このスクリプトだけを差し替えると、名前を尋ねずに登録できる。
- **登録の結果:** アプリが頼んだ登録（kc_action）の結果は、戻り先の `kc_action_status`（`success`、`cancelled`、`error`）で返る。取り消しや失敗でも、ログインは済み、認可コードも返る。
- **端末の認証器に限る:** `webAuthnPolicyPasswordlessAuthenticatorAttachment` を `platform` にすると、登録で、端末の認証器（Windows Hello など）だけを使わせる。端末に passkey がないまま passkey でのログインを始めると、Windows のダイアログは、スマートフォンの passkey を使う QR コードを出した。
- **JavaScript なしの登録とログイン:** 登録とログインのフォームは、`clientDataJSON` などの値を、ふつうのフォームの POST で受ける。ソフトウェアの認証器で作った値を送れば、ブラウザなしで通せた。ログインの `userHandle` は、利用者の ID の base64url で、画面の `userid` にある。

ほかの版と、ほかのブラウザでは確かめていない。
