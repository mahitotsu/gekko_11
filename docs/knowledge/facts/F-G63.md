# F-G63. Chromium 156 は、http の *.localhost を安全な文脈として扱い、RP ID を `app.<名前空間>.localhost` とする passkey の登録と署名、取り出せない WebCrypto の鍵が動いた

`http://app.secure.localhost:<ポート>` で、`isSecureContext` は真だった。RP ID を `app.secure.localhost` として `navigator.credentials.create` と `get` が成功し、`crypto.subtle.generateKey` で作った ECDSA の鍵は `extractable: false` だった。RP ID を `localhost` にした場合も成功した。名前空間の画面の基本の流れ（ログイン、passkey の登録、2 回の署名、提出、照合）が通った。

CDP の仮想の認証器は、`run-server` に `chromium.connect` でつないだブラウザでも使えた。

気をつける点: `page.route` の中の `route.fetch` は、ブラウザではなく `run-server` の Node が要求を出す。その Node は `*.localhost` を解決できず（`ENOTFOUND`）、失敗した要求は応答のないまま止まった。このリポジトリは、ブラウザのコンテナーの hosts に入口の名前を足し、書き換えに失敗したら要求を止める（test/ui）。

Windows の VS Code に内蔵されたブラウザでも、Windows Hello で passkey を登録できた（「Windows 端末に保存する」と示された）。2 回の署名と照合の一致まで通った。ほかのブラウザと、ほかの認証器では、確かめていない。
