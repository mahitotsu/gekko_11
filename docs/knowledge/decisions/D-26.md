# D-26. 直送の宛先は、顧客の端末が作る受信箱の番号とし、認可サーバーが本人の連絡先として持つ

**改訂（D-42）:** はじめは、顧客が passkey と一緒に登録した。passkey をログインサーバーに移したので、番号は、ログインの直後に、顧客のアプリの BFF が P で登録する。番号を宛先にする理由と影響は変わらない。

## 理由
直送は、本人が登録した連絡先へ送る（P-8、P-14）。顧客の名前で読める受信箱を、入口（D-25）から開くと、他人の契約内容を読めてしまう（要件 3 に反する）。端末が推測できない番号（128 ビット）を作り、ログインした本人の端末から登録すれば、番号を持つ端末だけが読める。

## 退けた案
- 顧客の名前を宛先のまま、入口から開く（他人の通知が読める）
- 受信箱を読むための、顧客のアプリ宛てのトークンを、別に受け取る（公開クライアントで、もう一度ログインの流れが要る。宛先を 1 つの窓口に絞る規則（D3a）と並べると、複雑になる）

## 影響
良い: 読むのに要るのは番号だけで、トークンも鍵も要らない。D18（登録済みの連絡先へ送る）の意味は変わらない。保険会社のシステムは、固定の連絡先の表を持たない。悪い: 番号が漏れると、その端末の受信箱が読める。番号は端末の保存領域に置く。端末ごとに登録するので、登録した端末の数だけ送る。

## 詳しい理由
認可サーバーは、`/contacts/inbox` で `{inbox}` を P と DPoP の proof と一緒に受け、`/internal/contacts/{user}` で、保険会社のシステムの SPIFFE ID にだけ返す。保険会社のシステムは、契約ごとに連絡先を引き、登録した全ての番号の `/notices/<番号>` へ送る。登録がなければ送らず、届かなかった記録を残す。
