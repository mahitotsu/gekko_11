# D-41. 顧客のアプリは BFF とし、トークンを画面に出さない

## 理由
ブラウザだけで OAuth を完結させる形は、個人情報を扱うアプリに推奨されない（F-G87）。画面でコードを動かされると、攻撃者が自分の鍵に結んだトークンを受け取り、画面を閉じた後も使える。BFF にすると、トークンは画面になく、奪われた認可コードもクライアントの資格がなければ替えられない（F-G89）。

顧客の承認は、端末の passkey の署名で示す（D-1）。そのため、BFF がトークンを持っても、承認は作れない。案の署名の確かめ（D22）、確認画面（D23）、写しと照合も、端末に残す。

## 退けた案
- ブラウザだけで完結させる（D-18）: 上の弱点が残る。
- Next.js の BFF にする: BFF の要点は、サーバーが機密クライアントになることで、フレームワークに依らない。今の配信元（Hono）が、すでに受信箱と提示の公開鍵を持つ。
- A を BFF の SVID（証明書）に結ぶ: ログインサーバーが SPIFFE の証明書を読まない（F-G81）。
- BFF のアプリが SVID の鍵で認可サーバーを直接呼ぶ: アプリは証明書の鍵を持たない、という組み立て（2-2）に反する。

## 影響
良い: 画面にトークンも鍵もなく、持ち出せない。奪われた認可コードと更新のトークンは使えない。営業 AI エージェントの入口がクラスタの外に出ない。悪い: 画面でコードを動かされると、画面が開いている間は、BFF を通して会話を進められる（F-G89）。BFF が乗っ取られると、ログイン中の顧客のトークンを使える。BFF のセッションはメモリにあり、複製を増やせない。

## 詳しい理由
- **クライアント認証:** 監査サービスと同じく、spiffe-helper が書き出す JWT-SVID を、`jwt-spiffe` の型で示す（D-38、F-G90）。
- **DPoP の鍵:** セッションごとに、WebCrypto の取り出せない鍵として作る。A と P を同じ鍵に結ぶ（D-42）。
- **Cookie と CSRF:** `__Host-Http-`、`Secure`、`HttpOnly`、`SameSite=Strict` で、事前確認の要るヘッダー（`x-bff`）と、自分の origin を求める（F-G89）。
- **転送先:** 画面からの要求は、AG-UI だけを、決まった出口へ送る。受信箱の番号は、BFF がログインの直後に認可サーバーへ登録し、画面から認可サーバーへの経路はない（D-42）。
- **htu:** 営業 AI エージェントは、内部の名前とパスで照らす。認可サーバーは、転送のヘッダーで URL を組み立てるので、`X-Forwarded-Proto` と `X-Forwarded-Port` を送る（F-G90）。ログインサーバーへの出口は、公開名の Host を付ける。
- **D21:** ID トークンは BFF が確かめる。トークンの応答はブラウザを通らないので、画面で差し替える手口と、その画面のテストはなくした。vulnerable で外す設定もない。
