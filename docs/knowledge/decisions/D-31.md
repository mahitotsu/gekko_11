# D-31. 監査の担当は、認可サーバーにログインし、監査サービスは SVID の mTLS で認証する OpenID Connect のクライアントになる

## 理由
監査の画面には、全ての顧客の契約と会話が出るので、見る人を確かめる必要がある。顧客を確かめている認可サーバー（D-19）を使い回せば、監査サービスに、別の利用者の名簿とパスワードを置かずに済む。認可サーバーは、ID トークンに、ログインした者の役割（roles）を載せる。監査サービスは、役割が監査の者にだけ画面を見せる。

監査サービスのクライアント認証は、ほかのサービスと同じく、SVID の mTLS（tls_client_auth）にする（D-7）。秘密の値を配らずに済む。認可コードは、confidential client でも PKCE で結ぶ。PKCE は認可コードの横取りを防ぎ（F-G21）、confidential client を対象とする FAPI 2.0 も S256 の PKCE を求める（F-G24）。

## 退けた案
- 監査サービスの中に、利用者とパスワードを置く: 認証の仕組みが 2 つになる
- client_secret で認証する: 秘密の値を配って守る手間が増え、ほかのサービスの認証と揃わない
- PKCE を使わない: 認可コードの横取りへの備えが減る
- 監査の画面を、クラスタの中からだけ開く（kubectl port-forward など）: 誰が見たかを、人の単位で確かめられない

## 影響
良い: 監査の担当も、顧客が使う入口と認可サーバーで確かめる。監査サービスは、秘密の値を持たない。悪い: 認可サーバーの既定の並びでは、PKCE と mTLS を一緒に使えないので、証明書の確かめを先に置くよう並びを変えた（F-G74）。監査の担当は、固定ユーザー（kansa）である。kansa は、顧客のアプリにもログインできるが、保険会社のシステムは顧客と認めないので、申し込めない。

## 詳しい理由
- **公開名と内部の名前:** ブラウザは、公開名の認可サーバー（`auth.<名前空間>.localhost`）でログインする。監査サービスは、トークンと公開鍵を、Envoy の出口（内部の名前）から取り、ID トークンの `iss` は公開名で確かめる。発見の文書は使わない（F-G73、D-25）。
- **戻り先:** 認可サーバーに登録する戻り先は、監査サービスの公開名（`audit.<名前空間>.localhost`）である。
- **トークンの要求:** 監査サービスは、`client_id` だけを付けて送り、Envoy の出口が SVID で mTLS をかける（F-G73）。
