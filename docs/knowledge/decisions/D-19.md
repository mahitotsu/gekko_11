# D-19. 認可サーバーは、Spring Authorization Server で作り、交換と結び付けの規則は、用意された拡張点で足す

## 理由
D-7 の結び直しに要る機能（`actor_token` と `may_act` の確認、交換の要求での DPoP、`tls_client_auth`、証明書に結んだトークン）を、OSS の標準の機能として持つ（F-G42）。`cnf` と `act` の入れ子は、標準の部品が書く（F-G49）。足すのは、宛先の確かめや SAN の URI の照合などで、用意された拡張点で書ける。

## 退けた案
- 自前の認可サーバー（製品の裏付けがない）
- Keycloak（結び付けたトークンを、出されたクライアント自身にしか替えさせない。F-G32）
- Curity（SPIFFE ID の照合は設定でできるが、商用で、結び直しを本文で確かめられなかった。F-G37）
- Auth0（結び直しを明記するが、クラウドだけで、手元の環境に置けない。F-G35）
- Microsoft Entra ID（RFC 8693 の交換がない。F-G38）
- node-oidc-provider（部品はあるが、交換の中身は自分で書く。F-G41）

この判断は、交換の認可サーバーの製品についてのものである。ログインと A の発行は、Keycloak に分けた（D-35）。下の表のうち、ログインの分は外し、A の取り込みを足した（D-36）。

## 影響
良い: 交換と結び付けの規則が、製品の機能と、その拡張点の上に乗る。悪い: 認可サーバーだけが Java になり、起動に時間がかかる。標準の部品には、使うときに差し替える点がある（F-G50、F-G51）

## 詳しい理由
### 足す拡張点
| 足すこと | 拡張点 |
|---|---|
| ログインサーバーが出した A を確かめて取り込む（D-36） | 交換の `AuthenticationProvider` を包む |
| `typ`、`aud`、取決めの範囲（RAR）、確認済みの属性、`may_act`（`iss` は URL の型で書く。F-G51） | `OAuth2TokenCustomizer` |
| 宛先の限定と、窓口ごとに替えてよい宛先、`actor_token` が替えを頼む者の証明書に結ばれていること、範囲を狭める処理 | 交換の `AuthenticationProvider` を包む |
| SAN の URI（SPIFFE ID）でのクライアントの照合 | 証明書の照合の部品 |
| 1 枚の連鎖を `tls_client_auth` として受け取る（F-G50） | 証明書の変換の部品 |
| 有効性の問い合わせで、`act` の連鎖の登録を確かめる | 有効性の問い合わせの差し替え |

### 製品を替えるとき
architecture は、認可サーバーに求める機能を、製品名なしで書く。製品ごとの対応は、事実 F-G32、F-G35〜F-G42 にある。
