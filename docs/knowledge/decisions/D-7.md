# D-7. トークンは全段で送信者の鍵に結ぶ。替える段では、替えを頼む者が自分の身元と鍵を示し、認可サーバーが代理を認可してから、その者の鍵に結び直す

## 理由
盗まれたトークンを、秘密鍵なしでは使えなくする（F-G4、F-G5、F-G16）。替えるトークンの鍵を、替えを頼む者は持たない。そのため、RFC 9449 §5 に従い、替える要求で示した鍵に、出すトークンを結び直す（F-G31）。Actor Profile の草案は、この結び直しを、新しい提示者の `actor_token` と所持の証明で行う手順として定める（F-G43）

## 退けた案
- Bearer のまま、短い有効期間だけで守る
- 顧客のアプリの段（A）だけを結び、B と C は mTLS で呼び出し元を限るだけにする
- 出されたトークンの持ち主と同じクライアントにだけ替えさせる（Keycloak の方式。F-G32）

## 影響
良い: どの段のトークンも、盗むだけでは使えない。替える段も、鍵を盗まなければ通らない。悪い: 正規の中継者の書き換えは防げない（D-1 と併用が要る）。前の段の鍵の来歴は確かめない（F-G43）。Keycloak では成り立たない（F-G32）

## 詳しい理由
### 段ごとの方式
| トークン | 結ぶ鍵 | 方式 | 確かめる者 |
|---|---|---|---|
| A | 顧客のアプリの鍵（ブラウザの取り出せない鍵） | DPoP（`cnf.jkt`） | 営業 AI エージェント |
| B | 営業 AI エージェントの証明書（X.509-SVID） | 証明書に結んだトークン（`cnf.x5t#S256`） | 事務サービス |
| C | 事務サービスの証明書（X.509-SVID） | 同上 | 保険会社のシステム |

顧客のアプリは、利用者の端末で動く公開クライアントであり、証明書を配れない（F-G24、F-G33）。そのため A だけ DPoP にする。サービスどうしは、SPIFFE の mTLS でつなぐので（D-16）、同じ証明書で結ぶ。

### 替える段の手順
1. 替えを頼む者は、SPIFFE ID の mTLS でクライアント認証する（`tls_client_auth`、F-G33、F-G45）。共有の秘密は使わない。
2. 替えを頼む者は、自分のトークンを `actor_token` として出す。
3. 認可サーバーは、出されたトークンの `may_act` と、`actor_token` の `sub` が一致することを確かめる。A の `may_act` は、顧客が同意した営業 AI エージェントである。B の `may_act` は、事務サービスである。
4. 認可サーバーは、出されたトークンの宛先が、替えを頼む者自身であることと、窓口ごとに替えてよい宛先であることも確かめる。
5. 出すトークンを、替えを頼む者の証明書に結ぶ。`act` に、替えを頼む者を積む（D-2）。

出されたトークンの鍵の所持は求めない。替えを頼む者は、その鍵を持たないからである。RFC 8693 と RFC 9449 は、この場合の方法を定めない（F-G31）。gekko_07 の検証では、結び直しが安全になる条件を、替えを頼む者を代理として独立に認可できることとしていた。`may_act` と `actor_token` が、その認可に当たる。

### 製品の裏付け
- **Auth0:** 結び付けを確かめ直さず、替えを頼む者の proof か証明書に結び直すと明記している（F-G35）。
- **Curity:** 交換の流れでも DPoP を使える（F-G37）。
- **Spring Authorization Server:** `may_act` と `actor_token` を確かめ、交換の要求の DPoP を確かめる。出されたトークンの `cnf` は拒否しない（F-G42）。このリポジトリは、これを使う（D-19）。
- **Keycloak:** 出されたクライアント自身にしか替えさせず、この方式は成り立たない（F-G32）。

結び付けの格下げ（Bearer で出すこと）を知らせる応答の `cnf` は、草案の段階である（F-G44）。受け取る側は、トークンの `cnf` を確かめ、結び付けのないトークンを拒む。

### 経緯
以前は、DPoP と mTLS のどちらを使うかを決めていなかった。次に、A だけを DPoP で結び、B と C は mTLS だけにすると決めた。自前の認可サーバーだけで成り立つ設計では説得力がないため、製品と標準の対応を調べ、全段の結び直しに改めた。
