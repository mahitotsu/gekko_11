# D-7. トークンの盗用は、サーバーどうしの段を mTLS で、顧客のアプリの段を DPoP で防ぎ、交換の段は鍵でクライアントを認証する

## 理由
盗まれたトークンを、秘密鍵なしでは使えなくする（F-G4、F-G5、F-G16）。トークンを替える段では、出されたトークンの鍵を、替えを頼む者は持たず、それを示す標準の方法もない（F-G31）。その段の守りは、替えを頼む者のクライアント認証で決まるので、認証を共有の秘密ではなく鍵で行う（F-G33、F-G34）

## 退けた案
- Bearer のまま、短寿命だけで守る
- DPoP だけで、全ての段を結ぶ
- mTLS だけで、顧客のアプリの段も結ぶ
- 出されたトークンの鍵の結び付きを、替えるときに確かめる

## 影響
良い: どの段でも、トークンを盗むだけでは使えない。替える段も、鍵を盗まなければ通らない。悪い: 正規の中継者の書き換えは防げない（D-1 と併用が要る）。サーバーごとに証明書の発行と更新が要る。Keycloak では、顧客のアプリの段のトークンを DPoP で結ぶと、営業 AI エージェントが替えられない（F-G32）

## 詳しい理由
### 段ごとの方式
| 段 | 結び付け | 交換でのクライアント認証 |
|---|---|---|
| 顧客のアプリ → 営業 AI エージェント（トークン A） | DPoP。顧客のアプリの鍵に結ぶ | —（顧客のアプリは替えない） |
| 営業 AI エージェント → 事務サービス（トークン B） | mTLS。営業 AI エージェントの証明書に結ぶ | 営業 AI エージェントが、mTLS で自分を示して A を B に替える |
| 事務サービス → 保険会社のシステム（トークン C） | mTLS。事務サービスの証明書に結ぶ | 事務サービスが、mTLS で自分を示して B を C に替える |

出すトークンは、要求したクライアントの鍵に結ぶ（F-G31 の RFC 9449 §5、F-G33 の RFC 8705 §3）。結び付きは、トークンを受け取るリソースサーバーが確かめる。A の結び付きは、営業 AI エージェントが、A を受け取るときに確かめる。

### 交換の段で、出されたトークンの鍵を確かめない理由
トークンを替えるのは、そのトークンを受け取ったサービスで、出されたトークンの持ち主ではない。RFC 8693 と RFC 9449 は、この場合に持ち主の鍵の所持を示す方法を定めない（F-G31）。そこで、認可サーバーは、次の 2 つで確かめる。

- 替えを頼む者を、鍵で認証する（mTLS、F-G33）。
- 出されたトークンの宛先が、替えを頼む者自身である。

RFC 8693 は、クライアント認証を省くと、盗まれたトークンを誰でも替えられると注意する（F-G31）。共有の秘密で認証すると、秘密とトークンを盗めば替えられ、この段だけ、ほかの段より弱くなる。鍵で認証すれば、鍵を盗まなければ替えられず、結び付けた段と同じ強さになる。

### 方式を段ごとに分ける理由
- **サーバーどうしは mTLS:** 同じ証明書を、クライアント認証と、トークンの結び付けの両方に使える（F-G33）。サーバーには証明書を配れる。秘密鍵で署名した JWT での認証（RFC 7523、F-G34）でもよいが、MAC も許すので、秘密鍵の署名に限る取り決めが要る。
- **顧客のアプリは DPoP:** 顧客のアプリは、利用者の端末で動く公開クライアントである。ブラウザは、証明書を求められると、利用者に選択画面を出す（F-G33）。FAPI 2.0 は、公開クライアントを対象にしない（F-G24）。

### 製品の制約
Keycloak 26.8 は、送信者に結んだトークンを交換に出せるのを、そのトークンを出されたクライアント自身に限る（F-G32）。A を DPoP で結ぶと、営業 AI エージェントは A を替えられない。Keycloak では、`act` を積む委任も preview である（F-G30、D-2）。このリポジトリの認可サーバーは、自前の実装である。

### 経緯
以前は、DPoP と mTLS のどちらを使うかを決めていなかった。token exchange と組み合わせるときに、出されたトークンの鍵を確かめられないことが分かり、段ごとに方式を決めた。
