# D-24. 防御を外す受け口は vulnerable のビルドだけに入れ、メモリ上で切り替えて読み返す。運用の受け口は、SPIFFE ID で呼べる者を限り、secure にも置く

## 理由
secure は、本番に近い形で動かす。そのため、切り替えの受け口は、ビルドの時点で除く（D-20）。シナリオは、70 通りほどの防御の組み合わせを確かめるので、Pod を入れ替えると 30 分以上かかり、認可サーバーの登録も消える。メモリ上で切り替え、切り替えた後と戻した後に設定を読み返して、効いていることを確かめる。

登録の失効と、契約の記録の読み出しは、secure にもある運用の機能である。共有の秘密ではなく、SPIFFE ID（運用の担当、監査の役）で呼べる者を限る。

## 退けた案
- 環境変数を変えて、Pod を入れ替える（確実さは高いが、時間と状態の再作成の費用が大きい）
- 共有の秘密（`INTERNAL_KEY`）と、確かめのための `/debug/state` を残す

## 影響
良い: secure のイメージに、防御を外す道がない。テストは、設定を読み返してから始める。悪い: 状態が回をまたいで残るので、テストは、その回の `nonce` で被害を絞る。

## 詳しい理由
トークンの確かめ（G1、G5〜G8、G20）、出口の交換（G2）、登録の有効性の問い合わせ（G10）は、token-guard に置く。問い合わせにはトークンそのものが要り、アプリはトークンを持たないからである。事務サービスには外す防御が残らないので、イメージは 1 つにする。
