# D-44. passkey の確認画面を待つ間は、待っていることを示して操作を止め、待ち時間そのものは縮めない

## 理由
Windows Hello の確認画面は、押してから Chrome で 1.8 秒ほど、VS Code に内蔵されたブラウザで 5 秒ほどで出る（F-G99）。その間に何も出ないと、利用者は押し損ないを疑う。押し直したり、ほかの操作をしたりすると、次のことが起きる。

- **署名:** 道具への答えが 2 回送られうる。
- **ページを離れる操作:** サインアウト、新しい申し込み、パスワードのフォームの送信は、ページを替え、passkey の要求を途中で切る。

そこで、押した直後に「端末の確認画面（PIN、指紋、顔）を待っています」と示し、次の操作を止める。

- **顧客のアプリ:** 署名のカードの「署名する」と「やめる」、「新しい申し込み」、「サインアウト」。署名は、入口で待っている間の二度目を断る。タブの切り替えは止めない。画面を隠すだけで、要求を切らないためである。
- **ログインの画面:** 隠しフォームを除く、全てのボタン、入力欄、リンク。Keycloak の標準のスクリプトを写して足す（登録のスクリプトと同じやり方。D-42）。結果によらずフォームを送ってページが替わるので、元に戻さない。

署名の要求の `allowCredentials` には、保険会社の一覧にある transports を添える（F-G100）。WebAuthn の仕様が RP に勧める形で、速さは変わらなかった（F-G99）。

ログインサーバーは、起動の引数 `--spi-theme--static-max-age=-1` で、テーマの静的なファイルをキャッシュさせない。写したスクリプトを替えても、ブラウザが 30 日前のものを使い続けたためである（F-G101）。

## 退けた案
- **hints（`client-device`）を添える:** Chrome での時間は、手のある・なしで変わらなかった（F-G99）。写した Keycloak のスクリプトが元から離れる分だけ、版を上げるときの比べ直しが増える。
- **ページを開いたときに認証器へ問い合わせる（`isUserVerifyingPlatformAuthenticatorAvailable()`）:** 同じく変わらなかった（F-G99）。
- **ログインで、利用者を特定してから passkey を頼む:** `allowCredentials` に識別子と transports を添えられる（F-G100）。ログインの流れを作り替える必要があり、署名で transports が効かなかったので、試していない。
- **ログインの画面で、passkey のボタンだけを止める:** 手の確かめで、待つ間も「Sign in」を押せた。押すとページが替わり、要求が切れる。
- **ログインの画面のひな形（ftl）を写す:** スクリプトから画面の要素を触れるので、要らない。写すファイルが増える。

## 影響
良い: 待つ間に、押せたかどうかが分かる。二度押しやページの移動で、答えが重なったり要求が切れたりしない。テーマを替えた配置が、すぐブラウザに届く。

悪い面は、次のとおりである。
- 待ち時間そのものは変わらない。デモでは外部のブラウザ（Chrome）のほうが短い。
- ログインの画面のスクリプトを写したので、Keycloak の版を上げるときに、元のファイルと比べ直す。
- ログインサーバーの静的なファイルは、毎回確かめ直しの要求が出る。教材の規模では問題にしない。
- 待ちの表示は、端末の確認画面が出たかを知らずに出す。ブラウザから、OS の画面が出たことは分からないためである。
