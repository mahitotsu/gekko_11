# D-28. 画面のテストは、Docker の Playwright のブラウザに手元の vitest からつないで行い、乗っ取られた営業 AI エージェントの返答はブラウザの手前で書き換える。画面の防御は、vulnerable の配信元の設定で外す

## 理由
- **ブラウザ:** 公式のイメージの `run-server` を、ホストのネットワークで動かす。手元にブラウザとシステムのライブラリを入れない。Java と Python も、同じ方針で Docker の中で使う。テストは手元の vitest から `playwright-core` でつなぐので、既存のクラスタのテストの部品（kubectl、防御の切り替え、監査の記録）を使える。passkey は、CDP の仮想の認証器が持つ（F-G63）。
- **返答の書き換え:** `/chat` と `/prepare` の返答を、ブラウザに届く手前で書き換える。secure と vulnerable で同じ手口を使え、営業 AI エージェントに書き換えの受け口を足さずに済む。
- **画面の防御の外し方:** vulnerable の顧客のアプリの配信元が、管理のポートで G21〜G23 の設定を受け、画面は開くときに自分の origin から読む。secure は、外す道のない版に置き換えてから画面をまとめる（D-24）。

## 退けた案
- 手元に Playwright のブラウザを入れる（システムのライブラリに管理者の権限が要る）
- テストの全体を、ブラウザのコンテナーの中で動かす（kubectl と kubeconfig をコンテナーに渡す）
- 営業 AI エージェントに、偽の提示と書類のすり替えの受け口を足す（secure では再現できない）

## 影響
良い: 画面の防御を、ほかのシナリオと同じ 4 種類の形で確かめられる。悪い: 画面の防御は、画面を開くときに読むので、テストは防御を外してから画面を開く。返答の書き換えは、ブラウザの外の Node が要求を出すので、入口の名前を hosts に足す（F-G63）。
