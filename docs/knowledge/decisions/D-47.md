# D-47. lint だけを入れ、整形の道具と Java の lint は入れない

## 理由
棚卸のときには、どの言語にも lint の設定がなかった。型の検査（`tsc --noEmit`）は通っていたが、`npm test` に入っていなかった。教材のコードは、防御を 1 つずつ外す悪い実装を含むので、使わない引数や変数、型の抜けが紛れると、読み手が意図を取り違える。lint は、その紛れを、機械で見つける。

規則は、各言語で広く使われる推奨のものだけにした。
- **TypeScript:** typescript-eslint の推奨。画面に、React の hooks の規則（rules-of-hooks、exhaustive-deps）を足した。画面のコードには、exhaustive-deps を理由つきで抑える注記が、前からあった。
- **Python:** ruff の既定の規則。
- **規則の調整:** secure の版の差し替えは、受け口と同じ形の引数を受けて使わないので、`_` で始まる名前を許す。テストは、型のない JSON の応答を読むので、`any` を許す。製品のコードの `any` は、型を書いて直した。

入れたときの指摘は、TypeScript で 25 件、Python で 0 件だった。直した中には、道具の答えの型（営業 AI エージェントの `ToolResult`）と、AI が送る道具の引数の型（顧客のアプリの画面）がある。どちらも `any` で、アプリが読む欄の型が、コードに書かれていなかった。型を書いても、実行時に形を確かめるわけではない。

## 退けた案
- **整形の道具（Prettier、ruff format、spring-javaformat）も入れる:** 全体を一度に整形すると、差分が大きく、履歴を辿りにくくなる。今の書式は、言語ごとにそろっている（TypeScript は 2 つの空白と二重引用符、Java は Spring の形のタブ、Python は 4 つの空白）。
- **Java にも lint（Checkstyle など）を入れる:** 今の形がそろっていて、型はコンパイラが確かめる。Maven のビルドへ足す手間に見合わない。
- **入れない:** 型の検査とテストだけでは、使わない変数と、`any` の紛れを見つけられない。

## 影響
良い: `npm test` が、型の検査と lint を、単体テストの前に回す。悪い: 書式（行の長さなど）は、機械では揃えない。120 字を超える TypeScript の行が、約 300 ある。
