# D-20. 全てのサービスを 1 つの k3d のクラスタで動かし、良い実装の secure と、防御を 1 つずつ外せる vulnerable の名前空間に分ける

## 理由
SPIFFE と Envoy でトークンを扱うので（D-16）、実物の基盤の上で確かめる。良い実装の側に切り替えの仕組みを置かないことで、本番に近い形だと言える。シナリオでは、防御を 1 つずつ外す確認と最小の漏れの組の確認をするので、悪い実装の側には、防御ごとの切り替えが要る。

## 退けた案
- 良い実装と悪い実装で、クラスタを 2 つにする（WSL2 の資源が足りない）
- 名前空間の名前を good と bad にする（検証でよく使う組の secure と vulnerable にする）
- プロセスの中だけで確かめる（Envoy と SPIRE を確かめられない）

## 影響
良い: 同じ操作の結果の違いを、2 つの名前空間で並べて見せられる。SVID と NetworkPolicy で、名前空間どうしを隔てられる。悪い: シナリオのテストに、クラスタが要る。速いテストは、内容の確かめだけになる。

## 詳しい理由
- **SPIRE:** 1 つで、両方の名前空間に SVID を配る。SPIFFE ID は `spiffe://gekko11.internal/ns/<名前空間>/sa/<サービス>` とする。
- **NetworkPolicy:** 全て拒否から始め、名前空間をまたぐ通信を許さない。
- **vulnerable の切り替え:** `token-guard`、アプリ、認可サーバーの管理の受け口で、防御を 1 つずつ外す。secure の版には、この受け口を組み込まない。
- **Envoy の切り替え:** Envoy 自身の検証は、再起動なしに切り替えられない（F-G46）。そこで、切り替えたい確かめは、`token-guard` に置く。`ext_authz` は、runtime の値で有効にする割合を変えられる（F-G47）。
- **シナリオのテスト:** 名前空間の中の Job として動かす。乗っ取られた営業 AI エージェントの役は、その SPIFFE ID を持つ。トークンを盗んだ第三者の役は、SVID を持たないか、別の SVID を持つ。
