# D-42. 顧客の passkey は 1 つとし、ログインと申込みの署名に使う

## 理由
署名だけに使う passkey を、ログインの直後に顧客のアプリで登録すると、利用者は「この passkey でログインしている」と取り違えやすい。ログイン用と署名用に分けると、端末に 2 つの passkey が並ぶ。1 つの passkey でログインと署名をすれば、利用者が覚える鍵は 1 つで、登録の画面で使い道を示せる。

ログインの画面（`login.<名前空間>.localhost`）と、署名の画面（`app.<名前空間>.localhost`）は名前が違う。WebAuthn は、RP ID を共通の親ドメインにすれば、両方で同じ passkey を使わせる（F-G91）。Keycloak は、親ドメインの RP ID で、登録とログインができた（F-G92）。名前の違うサイトどうしの共有（Related Origin Requests）は HTTPS が要り、TLS のない教材の入口では使えない（F-G91）。

passkey の登録はログインサーバーに任せ、顧客のアプリは、利用者が作ると決めたときに `kc_action` で頼む（F-G92）。いつ作成を促すかは D-43 で決める。必須の操作（required action）にすると、利用者ごとに 1 回しか出ず、2 台目の端末で登録できない。顧客のアプリは、ログインサーバーが返す登録の結果を見て、取り消しや失敗のときは、そう示す。

登録の画面は、Keycloak の標準の画面のまま使う。ただし、passkey の名前を `prompt()` で尋ねるスクリプトだけを差し替える。`prompt()` を使えないブラウザでは、登録が失敗するためである（F-G92）。名前には登録した日時を付け、同じ名前の拒否も避ける。登録は端末の認証器に限る（`platform`）。passkey は、署名する端末に置くためである。

ログインの画面は、開いただけでは passkey を使い始めず、「パスキーでログイン」を押したときだけ使う（mediation を `none` にする）。開いた時点の自動の待ち受けがあると、待ち受けの間にボタンを押したときに失敗した（F-G92）。ボタンだけにすれば、どのブラウザでも同じ流れになる。

保険会社のシステムは、公開鍵を、今と同じく認可サーバーに問い合わせ（`/internal/passkeys/{user}`）、認可サーバーは、ログインサーバーの管理の API から読む（F-G93）。認可サーバーは、監査サービスと同じく JWT-SVID でログインサーバーに認証し、利用者を読む役だけを持つ。

同じ passkey をログインにも使うので、ログインの署名を申込みの署名に使い回させない。保険会社のシステムは、署名の origin が顧客のアプリであること（D13）と、challenge が内容のハッシュであること（D-1）を確かめる。ログインの署名は、origin も challenge も違うので通らない。

受信箱の番号（D-26）は、passkey と切り離す。端末が番号を作り、BFF が、ログインの直後に P を使って認可サーバーへ登録する。利用者の操作は要らない。

## 退けた案
- 署名専用の passkey を、認可サーバーに登録したまま残す（D-37）: 上の取り違えが残る。
- ログイン用と署名用の 2 つの passkey を、それぞれ登録する: 利用者が、2 つの鍵の違いを覚える必要がある。
- 顧客のアプリとログインサーバーを同じ名前に置く: 入口の名前での振り分け（D-25）が崩れる。
- Related Origin Requests で、名前の違う 2 つのサイトを結ぶ: HTTPS が要る（F-G91）。
- passkey の公開鍵を、保険会社のシステムが Keycloak から直接読む: 保険会社のシステムに、ログインサーバーへの経路と管理の役が増える。

## 影響
良い: 利用者の passkey は 1 つで、登録の画面で使い道を示せる。登録したあとは、パスワードなしでログインできる。認可サーバーは passkey を記憶しないので、再起動で登録を失わない。ブラウザから認可サーバーへの経路がなくなる。

悪い面は、次のとおりである。
- ログインの署名と申込みの署名が、同じ鍵になる。違いは origin と challenge だけで、保険会社のシステムが origin を確かめ損なうと、使い回しを防げない。
- RP ID を親ドメインにするので、同じ親の下の別の名前（監査の画面など）でも、同じ passkey を使えてしまう。今は、監査の画面は passkey を使わない。ほかの名前の画面で作った署名も、保険会社のシステムが origin で断る。
- 認可サーバーに、ログインサーバーの利用者を読む役が要る。役は `view-users` だけにした（F-G93）。
- Keycloak の resident key の設定の不具合を、設定の組み合わせで避けている（F-G92）。版を上げるときに確かめ直す。
- 登録の画面のスクリプトを、Keycloak から写して直した。版を上げるときに、元のファイルと比べ直す。
- 登録を端末の認証器に限るので、スマートフォンの passkey（QR コードでつなぐもの）は、登録に使えない。ログインのダイアログには、OS がスマートフォンの選択肢を出すことがある。
