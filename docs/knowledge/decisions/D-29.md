# D-29. 顧客と営業 AI エージェントのやりとりは AG-UI 1.0 で行い、受け口は @ag-ui/core の型だけを使って自分で作る。顧客への質問と書類の提示は、画面側の道具とする

## 理由
営業 AI エージェントは、意向を聞いて案を示し、書類に同意を得て、代理で提出する。そのためには、AI と画面の間で文と道具の呼び出しを運ぶ決まりが要る。AG-UI は、この間をつなぐ標準で、画面側の道具（RunAgentInput.tools）の結果を tool message で返す決まりを持つ（F-G66）。事務サービスとの間の MCP とは、役割が重ならない。

受け口は、自分で作る。公式のアダプターは 0.0.x の版で、Claude Agent SDK の版を 1 つに固定することを求める（F-G67）。自分で作ると、Claude と台本の両方が、同じイベントを出せる。会話の往復ごとに、token-guard が作るトークンの控えも替えられる。SSE の書き出しは 1 行で済むので、弱点のある zod を取り込む encoder は使わない（F-G69）。

## 退けた案
- 公式のアダプター @ag-ui/claude-agent-sdk を使う（0.0.x で、版の固定を求める。台本は別に作る必要がある）
- 画面と営業 AI エージェントの間を、独自の JSON の受け口のままにする（標準で表せる流れを、独自の形で書くことになる）
- interrupt と resume で、顧客の答えを待つ（仕様の草案である。F-G66）

## 影響
良い: 営業 AI エージェントが、質問から提出まで進める流れを、標準の決まりで表せる。顧客の同意は、画面が示した書類への署名で返るので、AI の言い分に頼らない。悪い: 会話の状態は、営業 AI エージェントのメモリにあり、1 つの複製で動く前提になる。顧客が答えるまで、道具の呼び出しは待ち続ける（200 秒までは確かめた。F-G68）。トークン A は 5 分で切れるので、会話はその間に終える。切れたら、ログインし直して最初からやり直す（D-34）必要がある。

## 詳しい理由
- **画面側の道具:** `ask_customer`（質問と選択肢）、`present_offers`（署名つきの提示。画面が D22 で確かめてから示す）、`present_intent`（意向確認書面、署名 1/2）、`present_application`（申込書、署名 2/2）。
- **営業 AI エージェントの側の道具:** `get_offers`、`list_contracts`、`submit_application`（引数なし）。全て、Claude Agent SDK のプロセスの中の道具にする。事務サービスは、その回の token-guard の控えで呼ぶ。
- **回の区切り:** 画面側の道具を呼ぶと、`TOOL_CALL_START`、`TOOL_CALL_ARGS`、`TOOL_CALL_END` を出して、`RUN_FINISHED` で回を閉じる。次の回の tool message で、待っている呼び出しに答える。
- **会話の持ち主:** threadId を、トークンの `sub` に結び付け、ほかの顧客は続けられない。15 分使われなければ捨てる。
