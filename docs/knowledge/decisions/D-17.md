# D-17. 記録の監査は、記録を作る者と別の監査サービスが、認可サーバーと事務サービスの記録と突き合わせて行う

## 理由
窓口では、会社が営業員を監査し、記録を保存する（I-F1、I-G1）。記録を作る保険会社のシステムが、自分の記録を確かめても、書き換えは見つからない。第三者の記録と照らしてはじめて、確かめたことになる。

## 退けた案
- 保険会社のシステムの中に、監査の画面を置く

## 影響
良い: 保険会社のシステムの記録の書き換えや欠けを、交換の記録とツールの記録で見つけられる。悪い: サービスが 1 つ増える。監査で見つけたことに、人がどう対処するかは、運用に依る。

## 詳しい理由
監査サービスは、契約ごとに、次の記録を突き合わせる。記録は、各サービスが書き出し、Alloy が Loki に届けたものを読む（D-30）。保険会社のシステムの自己申告は、SPIFFE ID で限った受け口（`/audit/records`）から読む。
- 保険会社のシステムの契約の記録: 契約、`act` の連鎖、受け取ったトークン C の `jti`、申込みのハッシュ
- ログインサーバーと認可サーバーの記録: ログインサーバーが出した A（issue。D-39）と、認可サーバーが交換で出した B と C（exchange）。出したトークンの `jti`、交換の元の `jti`、替えを頼んだ者、`act`
- 事務サービスのツールの呼び出しの記録: 取り次いだ申込みの顧客と案と、事務サービスが算出した申込みのハッシュ
- 営業 AI エージェントの会話の記録: 自己申告として示し、根拠にしない（D-32）

確かめる点は、次の 7 つである。
1. 自己申告と、Loki の契約の記録が一致する
2. トークンの連鎖: C の `jti` から、交換の元を遡り、顧客のアプリへのログインの A まで、ログインサーバーと認可サーバーの記録でたどれる。道は、事務サービス ← 営業 AI エージェントの順で、本人は契約の顧客である
3. 経由: 契約の記録の経由と C の `act` が、交換の記録の道と一致する
4. 事務サービスの記録: 本人の依頼として、事務サービスがこの申込みを取り次いだ記録があり、受け取ったトークンが連鎖の B である
5. 申込みの中身: 契約の案と申込みのハッシュが、事務サービスが取り次いだ申込みと一致する
6. 会話: 示した申込みのハッシュが、事務サービスのハッシュと一致する（食い違いに気付くためだけ）
7. 書いた者: 関わる記録を、書いてよい者の Pod が書いた（D-32）

監査の画面は、監査の担当だけが見られる（D-31）。画面の冒頭は、根拠の強さごとに、何と何を比べたかと結果を示す。第三者の記録との比較、同じ書き手の記録どうしの比較、自己申告との比較、記録の書き手の 4 つである。同じ書き手どうしの一致は、独立した裏付けにならないので、分けて示す。比べる値がなかった点は、一致と見せず「比べていない」と示す。gekko_07 も、業務サービスの自己申告と、認可サーバーの記録を突き合わせる監査サービスを、別に立てていた。
