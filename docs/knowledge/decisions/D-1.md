# D-1. 取引内容の承認は、利用者の鍵による署名で行う

## 理由
通信路の保護と中継者の署名は、中継者が正規の送信者のとき、書き換えを防げない（F-G4、F-G5。F-G5 の部分は推定）

## 退けた案
mTLS だけ。AI や MCP による署名。取引ごとのトークン発行

## 影響
良い: 承認後の書き換えを検出できる。悪い: 署名前の確認画面の信頼に依存する（F-G8）

## 詳しい理由

### 内容の固定は、内容への署名で上回る
窓口では、書面に書かれた内容が依頼内容になる。しかし、書面が承認の後に書き換えられた場合の検出は、事務担当の目と技能に頼る（想定）。不審な箇所に気付けるかは、担当者の経験による。

紙の書類には、改ざんを防ぐ慣行がある。保険の申込書での運用は確認できなかった（I-A4）。目的に照らして、DX の手段と対応させる（推定）。

| 紙の手段 | 目的 | DX の手段 | 備考 |
|---|---|---|---|
| 訂正印と、削除・加入の文字数 | 誰が、どこを直したかを固定する | 署名済みの内容は直接直さない。変更は、新しい版として、新しい署名で残す | 重要な変更を覚書で行う慣行に当たる |
| 契印 | 複数ページの抜き取りと差し替えを防ぐ | 署名の対象に、全体（案の全体の識別子、申込内容）を含める | 部分の差し替えを検出できる |
| 割印 | 同じ内容の複数部の同一性を示す | 顧客の写しと保険会社の保管が、同じハッシュ値になる | 写しの見比べを、機械で行う |
| 大字、金額の前後の記号 | 金額の書き足しを防ぐ | 内容を正規化して署名する。書き足しは、ハッシュ値が変わる | 書き方の工夫が要らない |
| 捨印（弱点） | 軽微な訂正を省く | 事前に広い権限を与えない（D-2） | 紙では弱点。DX では悪い実装の例 |

DX では、承認する内容そのものに、利用者の鍵で署名する。内容を正規化して（JCS）ハッシュを取り、passkey の challenge にする方式が候補である。バックエンドは、提出された内容のハッシュが、署名した challenge と一致するかを確かめる。内容が 1 文字でも変われば、一致しない。

もう一つの候補は、SPC（F-G7）である。ブラウザが取引内容を自分の画面に出して同意を取り、署名付きの結果に取引内容が含まれる。`challenge` には入らず、`payment` 拡張で渡される。ただし、仕様は Candidate Recommendation Draft であり、決済に特化している（F-G7）。

**前提:** 署名の前に出す確認画面が、署名する内容そのものから作られる。WebAuthn 単体で、取引内容を認証器の画面に出す仕組みは、読んだ範囲で確認できなかった（F-G8）。確認画面の信頼は、アプリの実装に依存する。

### 方式の比較では、利用者の端末による署名だけが、中継者の書き換えを防ぐ
守る相手が中継者（AI）なら、利用者の端末が署名する方式だけが効く（推定）。署名の鍵を持つのが中継者自身なら、書き換えた内容にも正しい署名が付く。署名が示すのは「誰が送ったか」であり、「本人が何を承認したか」ではない。

| 方式 | 通信路の書き換え | トークンの盗用 | 中継者（AI）の書き換え |
|---|---|---|---|
| mTLS（F-G5） | 防げる | 証明書に結んだトークンなら、防げる | 防げない（推定） |
| DPoP（F-G4） | TLS に依存する。proof の対象は HTTP メソッドと URI だけ | 鍵を持たない第三者の再利用を防げる | 防げない |
| AI や MCP による HTTP の署名（F-G19） | 署名した構成要素については、防げる | 別の仕組みが要る | 防げない（推定） |
| 利用者の端末による署名（JWS、WebAuthn） | 防げる | 別の仕組みが要る | 防げる（鍵が端末から出ない前提） |

RFC 9421 は、中継者が通信を作り直して署名の対象を書き直すと、検証に失敗する（F-G19）。MCP は、バックエンドへ新しい要求を作る。そのため、AI から MCP への署名は、バックエンドまでは届かない（推定）。窓口間の通信の保護には使える（推定）。
