# D-25. ブラウザからの入口は、名前空間ごとの Envoy とし、http の app・login・auth・agent・audit の `*.<名前空間>.localhost` で受けて名前で振り分ける。issuer は入口の公開名にする

## 理由
顧客のアプリはブラウザで動く（D-18）ので、ブラウザがクラスタの中の 3 つの受け口（顧客のアプリの配信元、認可サーバー、営業 AI エージェント）に届く道が要る。ブラウザは、localhost を安全な文脈として扱いうる（F-G62）。Chromium では、http の `*.localhost` で passkey と取り出せない鍵が動いた（F-G63）。そのため、証明書なしで、手元の端末から画面を使える。

名前空間ごとに入口を置くと、secure と vulnerable の隔たり（D-20）を保てる。入口から先は、相手の SPIFFE ID を確かめる TLS で、証明書を示さない（顧客と同じ扱い。F-G59）。

## 退けた案
- Cloudflare Tunnel（名前付き）: 本物のドメインと HTTPS で、実際の端末の passkey を試せる。ただし、Cloudflare で管理するドメインとアカウントが要り、教材がインターネットに出て、自動テストが外部のサービスに頼る。後で、入口の名前を設定で替えて足せるようにする
- HTTPS と手元の認証局: 手で開くブラウザと、テストのブラウザの両方に、認証局を信頼させる手間がかかる
- kubectl port-forward: 長いテストの途中で切れやすい
- 名前空間で共有する入口: 名前空間をまたぐ経路が増える

## 影響
良い: 手元のブラウザだけで、ログインから照合まで試せる。入口の名前は `deploy/render.ts` の 1 か所で決まり、RP ID、origin、issuer、戻り先、CORS を、そこから作る。悪い: ブラウザと入口の間は TLS がない（利用者の端末の中のループバックに限る）。issuer が http になる。入口の名前は、手元の端末でしか引けない。

## 詳しい理由
- **名前とポート:** secure は 8081、vulnerable は 8082。k3d の loadbalancer から、入口の NodePort（30081、30082）につなぐ。
- **auth の受け口:** ブラウザに出す経路だけを通す（認可、トークン、jwks、設定の公開、ログイン、passkey の登録）。運用、内部、有効性の問い合わせは出さない。D-35 でログインがログインサーバーへ、D-42 で passkey の登録もログインサーバーへ移り、今はブラウザに出す経路がない。
- **issuer:** ブラウザが呼ぶ URL と一致させる。サービスは、これまでどおり内部の出口で認可サーバーを呼び、`iss` は公開名と照らす。
- **DPoP の htu:** 認可サーバーは、入口が付ける転送のヘッダーで、公開名を知る（F-G64）。営業 AI エージェントの token-guard は、設定した公開名とパスで照らし、転送のヘッダーに頼らない。
- **CORS:** 入口だけで扱う。事前確認には入口が答え、token-guard には届けない（F-G65）。
- **agent の受け口:** D-41 で、営業 AI エージェントは顧客のアプリの BFF からだけ受けるようにし、入口から外した。今の公開名は、app・login・auth・audit の 4 つである。
