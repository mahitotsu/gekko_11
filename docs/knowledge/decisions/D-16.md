# D-16. サービスの身元は SPIFFE の ID で表し、サービスどうしは X.509-SVID の mTLS でつなぐ

## 理由
共有の秘密をなくし、配置を確かめたサービスだけが、互いにつながれるようにする。証明書の SAN の URI が SPIFFE ID を持ち、RFC 8705 のクライアント認証と、証明書に結んだトークンの両方で、そのまま使える（F-G33、F-G45）

## 退けた案
- 共有の秘密（client_secret）でのクライアント認証
- 通信路の保護を、ヘッダーなどの模擬で表す
- JWT-SVID でのクライアント認証（使えるが、証明書に結んだトークンと別の仕組みになる）

## 影響
良い: 秘密を配らずに済む。証明書が、身元の確認とトークンの結び付けの両方に使える。悪い: 証明書を発行し、入れ替える基盤（SPIRE）が要る。正規のサービスである AI の書き換えは、防げない（D-1）

## 詳しい理由
各サービスは、相手の証明書の SAN の URI（SPIFFE ID）を、許した一覧と照らす。認可サーバーは、`tls_client_auth` で、登録した SPIFFE ID と照らす。SPIRE の SVID は、Subject がサービスによらず同じで、1 枚で示される（F-G52）。Spring Authorization Server は、既定では Subject DN で照らし、1 枚の連鎖を `self_signed_tls_client_auth` とみなす。そのため、証明書の照合と変換の部品を差し替える（F-G42、F-G50）。Curity は、設定で SAN の URI を照らせる（F-G37）。テストでは、テスト用の認証局が SPIFFE の形の証明書を作る。k3d の環境では、SPIRE が配る。試作で、この組み立てが成り立った（F-G55）。

### Envoy、token-guard、アプリの受け持ち
mTLS と SVID の扱いは、各 Pod の Envoy に任せる。SPIRE の agent が、SDS で SVID を渡す（F-G48）。Envoy の jwt_authn は、DPoP、`cnf` の結び付け、`typ` を確かめず、検証を再起動なしに切り替えられない（F-G46）。そこで、トークンの確かめは、Pod ごとの確かめのサイドカー（`token-guard`）が、Envoy の `ext_authz` として受け持つ（F-G47）。

| 受け持つ者 | 確かめること |
|---|---|
| Envoy | mTLS（信頼する認証局）、`ext_authz` の呼び出し、出口での相手の SPIFFE ID への接続 |
| `token-guard` | 相手の SPIFFE ID、トークンの署名・`iss`・`aud`・`exp`・`typ`、DPoP、`cnf` の結び付け、出口でのトークンの交換 |
| アプリ | 内容（署名の連鎖、内容の一致、案の署名、`nonce`、取決めの範囲、`sub` から顧客を決めること、記録） |

アプリは、トークンも証明書も持たない。`token-guard` が確かめた主張だけを使う。gekko_07 も、Envoy のサイドカーと `ext_authz` で、トークンを替え、確かめていた。
