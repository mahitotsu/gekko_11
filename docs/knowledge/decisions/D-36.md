# D-36. 認可サーバーは、交換に出された A をログインサーバーの公開鍵で確かめ、保存先に取り込んでから、標準の部品に渡す

## 理由
標準の部品は、保存先にあるトークンしか替えない（F-G77）。確かめてから保存先に入れれば、後の処理は、自分が出したトークンと同じ部品で動く。宛先の確かめと `may_act` の照合、結び直し、`act` の記録が、後の処理である。

確かめるのは、署名（RS256）、`iss`（ログインサーバーだけ）、`typ`（`at+jwt`）、期限である。加えて、`azp` が顧客のアプリで、`sub` と `may_act` があることを求める。`may_act` の `iss` は、標準の部品に合わせて URL の型に直す（F-G51）。公開鍵は、相手の SPIFFE ID を確かめる Envoy の出口から取る。

## 退けた案
- 交換の部品を丸ごと書く: 標準の部品の確かめを自分で持つことになる
- 交換のたびに Keycloak へ有効性を問い合わせる: 問い合わせのクライアントを別に用意することになる。A は 5 分で切れる

## 影響
良い: 標準の部品と記録を変えずに済む。悪い: 取り込みは自作で、信頼の境界にある。そのため、防御 D28 とシナリオ 25 で確かめる。ログインサーバーで終わらせたログインの A も、期限までは替えられる。A は替えるときに保存する。替えられる前の A は、有効性の問い合わせで有効と答えられない。
