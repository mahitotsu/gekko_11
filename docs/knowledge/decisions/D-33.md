# D-33. サインアウトは、RP-Initiated Logout で、アプリと認可サーバーの両方のログインを終わらせる

## 理由
顧客のアプリと監査サービスは、同じ認可サーバーにログインする（D-18、D-31）。アプリのセッションだけを消しても、認可サーバーのログインが残り、次のログインは、前の人のまま通る。同じブラウザで顧客と監査の担当を替えられず、顧客のまま監査の画面を開くと、断られた画面から抜け出せない。

そこで、アプリは、自分のセッションを消してから、ブラウザを認可サーバーの `/connect/logout` へ送る。このとき ID トークンを示す。認可サーバーはログインを終わらせ、登録された戻り先へ戻す。監査サービスは、断る画面（403）にも、サインアウトを置く。

ID トークンを確かめられないときは、登録された戻り先へ戻す（F-G76）。多くは、認可サーバーの再起動で記憶が消えた場合で、終わらせるログインも残っていない。

## 退けた案
- アプリのセッションだけを消す: 次のログインが、前の人のまま通る
- 利用者が Cookie を消す: 操作を選べないブラウザがあり、手順として案内できない
- ID トークンを確かめずにログインを終わらせる: ほかのサイトから、利用者を勝手にサインアウトさせられる
- 確かめられないときに、標準の 400 のまま: ログインの画面へ送られ、ログインすると、入口の 404 で行き止まりになる

## 影響
良い: 同じブラウザで、利用者を替えられる。悪い: サインアウトしても、もう一方のアプリのセッションは残る。front-channel と back-channel の logout は作っていない。ID トークンを確かめられないときは、認可サーバーのログインが残っていても終わらせない。例えば、別の人の ID トークンを持つ画面からのサインアウトである。

## 詳しい理由
- **戻り先:** ログインの戻り先と同じ名前の、画面の先頭を登録する。登録にない宛先へは戻さず、400 を返す。任意のサイトへ送る踏み台にしない。
- **端末の記録:** 顧客のアプリのサインアウトは、セッションだけを消す。passkey の識別子、受信箱の番号、写しは、人ごとに端末で保つ。
- **入口:** 認可サーバーの公開の経路に、`/connect/logout` を足す。
