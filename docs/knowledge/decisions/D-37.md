# D-37. passkey と受信箱の登録は認可サーバーに残し、本人の確かめは、ログインサーバーが prompt=none で出す専用のトークン P と DPoP で行う

**廃止（D-42 で置き換え）:** passkey の登録は、ログインサーバーに移した。ログインと申込みの署名で、同じ passkey を使うためである。受信箱の番号の登録と、本人の確かめに P と DPoP を使うことは、D-42 が引き継ぐ。下の「退けた案」の 2 つ目は、Keycloak の passkey では RP ID が違うことを理由にした。RP ID を共通の親ドメインにすると、この理由は成り立たない（F-G91、F-G92）。

## 理由
ログインが移ると、認可サーバーのログインセッションでは本人を確かめられない。A の宛先に認可サーバーを足すと、D3a の 1 つの宛先が崩れる。そこで、任意のスコープ `passkeys` を分け、ログインしたまま、宛先が認可サーバーのトークン P を受け取る（F-G79）。P は A と同じ DPoP の鍵に結び、受け口はリソースサーバーとして確かめる（F-G82）。

## 退けた案
- 認可サーバーを Keycloak のクライアントにして、ブラウザのセッションを作る: confidential client の認証がもう 1 つ要り、画面の遷移も増える
- 登録を Keycloak の passkey に任せる: Keycloak の passkey はログインのためのもので、RP ID も違い、申込みの署名に使えない
- 登録を保険会社のシステムに移す: 保険会社のシステムに、ブラウザからの経路が増える

## 影響
良い: A の宛先を広げない。受け口は Cookie を使わない。悪い: ログインのたびに、画面の外でリダイレクトが 1 往復増える。P は 5 分で切れるので、登録の前に切れていたら受け取り直す。P には、前回の取決めの範囲も載るが（F-G78）、受け口は読まない。
