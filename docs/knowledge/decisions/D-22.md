# D-22. サービスごとに言語を選ぶ。保険会社のシステムと監査サービスは Java、事務サービスは Python の FastMCP、営業 AI エージェントは TypeScript、顧客のアプリは Web にする

## 理由
k3d で動かすので、サービスを同じ言語にそろえる必要がない（D-20）。業務のバックエンドで広く使う Java と、MCP のサーバーで実績のある FastMCP を選ぶ。営業 AI エージェントは、Claude Agent SDK のある TypeScript にする。教材の説得力が上がる。防御が、共通のライブラリではなく、標準（JWT、JCS、WebAuthn、mTLS）だけで成り立つことも示せる。顧客のアプリが TypeScript で署名した内容を、Java の保険会社のシステムが検証する。

## 退けた案
- 全てを TypeScript にそろえる（標準での相互運用を示せない）
- 顧客のアプリを Flutter のモバイルのエミュレーターにする（passkey に Google のアカウントとドメインの関連付けが要り、手元の資源も足りない見込み。鍵を Android の Keystore に置くので、D-18 を直すことになる）

## 影響
良い: トークンの確かめは token-guard がそろえるので、言語に依らない。標準での相互運用を、テストで確かめられる。悪い: ビルドが 3 種類になる。Java のサービスはメモリを多く使う。部品の依存の食い違いも起きる（F-G58、F-G61）。

## 詳しい理由
監査サービスは、保険会社のシステムと同じ Spring Boot で、画面まで持つ簡易アプリにする（段 3）。記録の集約は、Loki と Alloy にする。Promtail は保守が終わっている。
