# ナレッジの索引と使い方

このリポジトリの文書やコードが依拠する事実、設計の判断、設計のメモを、1 件 1 ファイルで持つ。この索引は、その一覧と、使い方の規則である。

**この文書の読み手:** このリポジトリで文書やコードを直す AI エージェント（Claude Code など）。人が読んでもよいが、人向けの説明は docs/ 直下の文書にある。読んだ後に、主張を書く前に根拠と確認度を引き、事実や判断を正しい形で足し、直せる。

## 要旨
- **事実（facts/）:** 調べて確かめた事実。52 件。ID は、窓口が `I-`、仕様が `F-G`、共通が `C-`、未調査が `I-X`。
- **判断（decisions/）:** 設計の判断と、退けた案、悪い面。27 件。ID は、領域に依らない判断が `D-`、提案型で足す判断が `P-`。
- **設計のメモ（notes/）:** 判断に入らない、設計の整理。4 件。
- **確認度で、書き方が変わる:** 本文確認だけを、事実として書ける。確認できず・未調査の事実は、事実として書かない。
- **文書は ID で参照し、本文を写さない:** 事実を直したら、その ID を使っている文書を確かめる。

## 使い方の規則
### 主張を書く前に
1. 文書に事実を書く前に、下の索引か `grep -rn "<言葉>" docs/knowledge/facts` で、該当する事実を探す。
2. 見つからなければ、調べて、事実を 1 件足す（下の「足し方」）。調べられないなら、その主張は書かない。
3. 文書には、事実の ID を括弧で添える（例: 「本人確認書類で確かめる（I-B6）」）。事実の本文は写さない。

### 確認度の扱い
| 確認度 | 意味 | 文書での書き方 |
|---|---|---|
| 本文確認 | 一次資料の本文を読んで確かめた | 事実として書き、ID を添える |
| 要約のみ | 検索結果や解説の要約でしか確かめていない | 書けるが、依拠する前に本文を読む。重要な結論の唯一の根拠にしない |
| 確認できず | 探したが、公開資料で見つからなかった | 事実として書かない。窓口の話で使うときは、[窓口のたとえ話の中身と根拠](notes/window-story.md)の区別の表に「想定」として入れる |
| 未調査 | 調べていない | 事実として書かない |

- 推定（事実から導いた見立て）は、技術の文書（architecture 以降）では、根拠の ID を添えて「推定」と書く。purpose.md では、本文に「推定」を散らさず、たとえ話の断り書きと、窓口のたとえ話のメモの区別の表で代える（CLAUDE.md の約束）。
- 窓口の話（purpose.md）と、このリポジトリの実装の話を、同じ文に混ぜない。

### 足し方と、直し方
- **事実を足す:** `facts/<ID>.md` を、既存のファイルと同じ形で作る。先頭の項目は `読み手`、`id`、`主張`、`確認度`、`分野`、`出典`（一次か二次か、URL、読んだ箇所、取得日）。本文は、結論と、必要なら折りたたみの補足。ID は、同じ接頭辞の末尾の番号の続きにする。
- **判断を足す:** `decisions/<ID>.md` を作る。先頭の項目は `読み手`、`id`、`判断`、`状態`（提案 / 承認 / 廃止）、`根拠`（事実の ID）。本文は、理由、退けた案、影響（良い面と悪い面）。理由は事実で書き、価値判断を混ぜない。
- **直す:** 事実の確認度や結論を変えたら、`grep -rn "<ID>" docs README.md` で使っている文書を洗い出し、書き方を確認度に合わせて直す。この索引の表も直す。
- **消さない:** 誤りと分かった事実や、取り下げた判断は、ファイルを消さずに、確認度や状態を直し、理由を本文に書く。ID を使い回さない。

## 未確認の事項
- I-A3、I-B4、I-D2 に挙げた運用。公開資料では見つからない。保険会社の事務規程、募集人向けの手引、実務経験者への聞き取りで確認する。
- 要約のみの項目の本文。特に I-B3、I-D1、I-E1、I-H1。
- 監督指針の本文は、要約モデルを介して読んだ。重要な項目は、原文を直接読んで確かめる。
